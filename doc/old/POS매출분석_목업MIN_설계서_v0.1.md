## 1. 목적과 포지셔닝 — 이 목업은 무엇을 증명하는가

목업의 목적은 성능·보안 증명이 아니라 **"화면과 행동 카드가 현장에 말이 되는가"를 하루 만에 눈으로 확인 가능하게 만드는 것**이다.

| 구분 | 정식 설계서 v1.3 | 본 목업 (MIN) |
|---|---|---|
| 데이터 원천 | 기간계 Oracle (파티션·Watermark) | 샘플 엑셀 + 합성 데이터 생성기 |
| 저장소 | DuckDB→PostgreSQL | **SQLite 기본** / Supabase(PostgreSQL) 선택 |
| 기간·규모 | 13개월, 점포 1~3곳 실데이터 | 합성 13개월 × 점포 3곳 (수십만 행 이내) |
| 화면 | 점포장+운영자+관리자 4종 | 점포장 화면 1종 (Day-1) |
| AI | 로컬 LLM+템플릿+주장 검증 | 템플릿 모드 (LLM은 2주차 옵션) |
| 검증 대상 | Hard/Adoption/재사용 Gate | 화면 이해도·카드 적합성·데이터 흐름 완결 |
| Oracle 연동 | 핵심 범위 | **목업 이후 추가 사항** (8장에 확장 설계만 선반영) |

**목업이 증명하지 않는 것(정직한 한계)**: 기간계 무부하 추출, 대용량 성능, 보안 심의 요건, 실측 Baseline. 이는 정식 트랙의 몫이며 목업 결과로 주장하지 않는다.

## 2. MIN 범위 정의 — 하루 / 2주 / 이후

### 2.1 Day-1 필수 (이것만 되면 목업 성공)

| # | 기능 | 완료 기준 |
|---|---|---|
| M1 | 합성 데이터 생성기 | 점포 3곳 × 13개월 영수증/상품/결제 생성 (실샘플 패턴 반영: 아침 피크, 요일 효과, 소량 구매 1.4줄/영수증) |
| M2 | FACT 3종 적재 (SQLite) | FACT_RECEIPT / FACT_RECEIPT_ITEM / FACT_PAYMENT — 정식과 동일 스키마·컬럼명 |
| M3 | 일 집계 마트 + 요약 캐시 | MART_DAY_STORE(_ITEM) + 점포별 오늘의 요약 JSON |
| M4 | 점포장 화면 (Streamlit 1페이지) | 세 층: ①총매출+증감 문장 ②건수×객단가 ③TOP5 + 시간대 미니 차트, 데이터 기준일 표시 |
| M5 | 행동 카드 (템플릿 모드) | 규칙 3종(G2 시간대·G4 구조분해·G6 무제안) → [현상→해석→행동→근거] 카드 0~3개, [할게요/괜찮아요] 버튼 |

### 2.2 2주 내 보강 (W1~W2)

간이 품질 대사(키 중복·ITEMCNT 대사) → 피드백 로그 저장 → 일일 보고 1종(엑셀 다운로드) → 규모 그룹 비교선 → 로컬 LLM(Ollama) 옵션 + 주장 검증기 min → 운영자 품질 미니 화면 → Supabase 전환 시험(선택) → 데모 시나리오·문서화

### 2.3 목업 이후 추가 사항 (본 목업 범위 제외 — 8장에 확장 설계)

Oracle 연동(대용량 추출·Watermark·STAGE 승격), 보안 심의·인증, 권역/본사/경영진 화면, 주·월 보고, 5년 보관·이관, 상용 API Provider

## 3. 아키텍처 — 작지만 정식과 같은 모양

```text
[데이터 소스 계층 — Extractor 인터페이스]
  SampleExtractor(합성+샘플엑셀)   ←Day-1
  OracleExtractor(파티션·청크)     ←목업 이후 (인터페이스만 정의)
        ↓ extract(from_date, to_date) → 청크(DataFrame) 반복자
[적재 파이프라인 — 기간 재생성]
  load(--from --to): DELETE→INSERT (날짜 단위 멱등)
        ↓
[저장소 계층 — Repository (SQLAlchemy)]
  SQLite(기본, 파일 1개)  ↔  Supabase PostgreSQL(URL만 교체)
        ↓
FACT 3종 → MART → 요약 캐시(JSON)
        ↓
[화면] Streamlit 점포장 1페이지  +  [카드] 템플릿 엔진(규칙은 코드)
```

**저장소 선택 기준**: Day-1은 **SQLite** — 설치 0분, 파일 1개, 로컬 완결이라 하루 목표에 최적. **Supabase**는 ① 외부 시연 URL이 필요하거나 ② PostgreSQL(정식 확산 경로) 이식성을 미리 확인하고 싶을 때 W2에 전환 시험한다. 코드는 SQLAlchemy 접속 URL 교체만으로 두 저장소를 오가도록 작성한다(방언 종속 SQL 금지).

## 4. Oracle 대용량을 염두에 둔 설계 원칙 5 (목업 코드에 지금 심는 것)

목업 이후 Oracle을 붙일 때 "다시 짜는" 것이 아니라 "Extractor만 갈아 끼우는" 구조를 만들기 위해, Day-1 코드부터 다음을 지킨다.

1. **스키마·컬럼명 동결**: FACT·MART의 테이블/컬럼명은 설계서 v1.3 정의(SALEDATE, DEPT_CD, POSNO, DEALNO, SEQ, ITEMCNT, TENDERCNT…)를 그대로 쓴다 — 합성 데이터도 실컬럼명으로 생성한다.
2. **Extractor 인터페이스 고정**: `extract(from_date, to_date) → 청크 반복자`. SampleExtractor와 미래의 OracleExtractor(파티션 단위 읽기·fetch size·스로틀·세션 1 파라미터 자리 포함)가 같은 계약을 따른다.
3. **청크 스트리밍 습관화**: 목업 데이터가 작아도 전량 메모리 적재를 금지하고 청크(예: 5만 행) 단위로 적재한다 — 대용량에서 터지는 코드를 목업부터 만들지 않는다.
4. **기간 재생성 시그니처 유지**: `--from/--to` 파라미터의 단일 파이프라인(일일·수동·이관 공용) 구조를 목업에서 그대로 구현한다.
5. **Watermark·STAGE 자리 선확보**: 목업에선 사용하지 않지만 `ETL_WATERMARK` 테이블과 STAGE 스키마를 생성해 두고, 적재 함수에 승격 단계 훅(hook)을 빈 함수로 남긴다 — Oracle 연동 시 채워 넣기만 하면 된다.

## 5. 데이터 설계 (MIN)

- **FACT_RECEIPT**(영수증 1행): DEPT_CD, SALEDATE, POSNO, DEALNO, SALETIME, DEALTYPE, ITEMCNT, 합계금액
- **FACT_RECEIPT_ITEM**(상품 1행): +SEQ, PLU_CD, GOODS_NM, ITEM_HEAD/MEDIUM/DETAIL(+명), SALEPRICE, QTY, SALEAMOUNT, DC_YN
- **FACT_PAYMENT**(결제 1행): +TENDERSECTION, TENDERAMOUNT, TENDERDATA99(카드사명만)
- **MART_DAY_STORE / MART_DAY_STORE_ITEM / (W1) MART_HOUR_STORE**, **SUMMARY_STORE_DAILY**(요약 JSON), **FEEDBACK_LOG**(W1)
- 개인정보 컬럼은 합성 단계부터 아예 생성하지 않는다(원천 미적재 원칙의 목업판)
- **합성 데이터 규칙**: 실샘플(DATA_*.xlsx)에서 상품·분류·가격 사전을 추출하고, 시간대 분포(아침·점심 피크)·요일 계수·계절 진폭을 곱해 13개월 생성. 점포 3곳은 대/중/소 규모 차등. 취소 거래를 소량(1~2%) 포함해 상계 로직 시연 가능하게.

## 6. 화면·카드 설계 (MIN)

**점포장 화면 1페이지(Streamlit)**: 상단 데이터 기준일 → 1층 어제 매출+증감 문장("어제보다 12% 늘었어요", 색+아이콘+문장) → 2층 손님 수×객단가("손님이 늘었어요") + 시간대 미니 차트 → 3층 TOP5 → 행동 카드 0~3개 → (W1) 보고서 다운로드. 글자 크게(18px+), 버튼 크게, 스크롤만으로 전부 도달. 점포 선택은 데모용 셀렉트박스(3곳).

**행동 카드 규칙 3종(코드가 판정, 템플릿이 문장화)**:

| 규칙 | 발동 조건 | 템플릿 예 |
|---|---|---|
| G2 시간대 | 특정 시간대 매출 비중 ≥ 기준 | "오전 {h}시대에 하루 매출의 {p}%가 나와요. 그 전에 진열을 확인하세요" |
| G4 구조 | 증감 원인의 건수/객단가 분해 | "매출 변화는 손님 수보다 1인당 구매액 영향이 커요" |
| G6 무제안 | 발동 없음 | "오늘은 평소대로 하시면 됩니다" |

숫자는 전부 계산 JSON에서 치환 — 템플릿 모드이므로 환각이 원천 불가능하고, W2에 LLM을 붙일 때 같은 JSON에 주장 검증기를 더한다.

## 7. 2주 로드맵

### Day-1 시간 계획 (목업 완성일)

| 시간 | 작업 |
|---|---|
| ~2h | 프로젝트 골격 + SQLite 스키마(FACT·MART·Watermark 자리) + Extractor/Repository 인터페이스 |
| ~4h | 합성 데이터 생성기(실샘플 사전 추출 포함) → 13개월 적재 |
| ~6h | 집계 마트 + 요약 캐시 계산 |
| ~8h | 점포장 화면 세 층 + 카드 3종 → 데모 가능 상태 |

### W1 (2~7일): 간이 대사 → 피드백 로그 → 일일 보고 엑셀 → 규모 비교선 → 코드 정리(코딩 표준·테스트)
### W2 (8~14일): Ollama 옵션+주장 검증 min → 운영자 미니 화면 → Supabase 전환 시험(선택) → 데모 시나리오 리허설 → 목업 회고·정식 트랙 반영 목록 작성

## 8. 목업 이후 추가 사항 — Oracle 대용량 연동 확장 설계 (선반영)

| 확장 항목 | 목업에 이미 준비된 것 | 이후 작업 |
|---|---|---|
| OracleExtractor | 인터페이스·청크 계약 | 파티션 단위 SELECT(SALEDATE 파티션), fetch size 튜닝, 스로틀·세션 1, 야간창 가드 |
| 증분 | ETL_WATERMARK 테이블 | REG_DATE Watermark + 영향일자 + 안전중첩 7일 로직 활성화 |
| 안전 적재 | STAGE 스키마·승격 훅 | STAGE 검증 후 원자적 승격 구현 |
| 저장소 승격 | SQLAlchemy 추상화 | SQLite→PostgreSQL 전환(Supabase 시험으로 사전 검증됨) |
| 대량 이관 | `--from/--to` 파이프라인 | 표본 구간 성능 실측 → 13개월→5년 분할 이관 |
| 품질·보안 | 간이 대사, 개인정보 미생성 | 게이트 7단계 전체, 컬럼 심사표, 인증·권한 |

## 9. 목업 성공 기준 (데모 시나리오)

1. 점포를 고르면 3초 안에 "어제보다 ○% 늘었어요" 화면이 뜬다
2. 카드의 모든 숫자가 화면 수치와 일치한다 (템플릿 치환 — 불일치 0건)
3. 날짜를 바꿔도(재적재 두 번) 결과가 동일하다 (멱등 시연)
4. `--from/--to` 재생성 명령이 동작한다 (Oracle 확장 경로의 실물 증거)
5. 시연자가 "이건 목업 데이터이고, 실데이터 연동은 이후 단계"임을 화면 배지로 안내한다
