# ADR-0007. 브리핑 템플릿 해석과 계산 JSON 필드 보강

- 상태: 채택 (⚠️ 1번 항목은 사용자 확인 권장)
- 일자: 2026-08-27
- 관련 마일스톤: M4

## 배경

명세 7.4는 브리핑 3줄의 문자열을 확정하고, 명세 14장은 **"브리핑 문구 임의 개선 금지
(7.4 문자열 준수 — 개선 제안은 별도 보고)"** 라고 못 박았다. 그런데 그 7.4를 코드로 옮기려니
글자 그대로는 결정되지 않는 지점이 둘 있었다.

## 결정 1. 변형 B의 1줄도 "어제 {sale_amt:,}원 — " 접두를 공유한다

### 문제

명세 7.4의 1줄 기본형(변형 A)과 로테이션 변형(변형 B)은 이렇게 적혀 있다.

| | 상승 | 하락 | 보합 |
|---|---|---|---|
| **변형 A** | `어제 {sale_amt:,}원 — 평소 {dow_name}보다 {dow_diff_pct}% 좋았어요 🔺` | `... {abs}% 아쉬웠어요 🔻` | `어제 {sale_amt:,}원 — 평소 {dow_name} 수준이었어요` |
| **변형 B** | `평소 {dow_name}보다 {dow_diff_pct}% 잘 나온 하루였어요 🔺` | `평소 {dow_name}보다 {abs}% 조용한 하루였어요 🔻` | `평소 {dow_name}과 비슷했어요` |

변형 B의 문자열에는 **금액이 없다.** 글자 그대로 구현하면 절반의 날에는
"어제 얼마 팔렸는지"가 브리핑 1줄에서 사라진다.

### 결정

변형 B의 1줄에도 `어제 {sale_amt:,}원 — ` 접두를 붙인다. 최종 문자열은 이렇게 된다.

```text
변형 A 상승: 어제 3,039,200원 — 평소 수요일보다 12.0% 좋았어요 🔺
변형 B 상승: 어제 3,039,200원 — 평소 수요일보다 12.0% 잘 나온 하루였어요 🔺
변형 A 보합: 어제 3,039,200원 — 평소 수요일 수준이었어요
변형 B 보합: 어제 3,039,200원 — 평소 수요일과 비슷했어요
```

### 근거

- **명세가 스스로 접두 생략 표기를 쓴다.** 변형 A의 하락형이 `"... {abs}% 아쉬웠어요 🔻"` 로
  적혀 있다. 여기서 `...` 는 앞선 `어제 {sale_amt:,}원 — 평소 {dow_name}보다` 를 줄인 것이다.
  같은 문서가 같은 절에서 접두를 생략해 적는 관행을 쓰고 있으므로, 변형 B도 **바뀌는 뒷부분만**
  적은 것으로 읽는 것이 자연스럽다.
- **폴백 규정이 접두를 문장의 뼈대로 다룬다.** 명세 7.4는 표본 부족 시
  *"1줄은 「어제 {sale_amt:,}원이었어요」로 축약하고 dow 비교 문구를 생략한다"* 고 적었다.
  즉 `어제 {금액}원` 이 1줄의 몸통이고 요일 비교가 덧붙는 부분이라는 구조를 명세가 이미 밝혔다.
  변형은 덧붙는 쪽에 걸리는 것이지 몸통을 걷어내는 것이 아니다.
- **1줄의 역할이 "결과(항상)"** 다. 명세 7.4가 1줄에 붙인 이름이 그렇다. 금액 없는 결과 보고는
  이 역할과 맞지 않는다. 데모의 첫 문장이 매출을 말하지 않는 날이 절반이면 제품 자체가 흔들린다.
- 2줄 변형 B는 사정이 다르다. `{name} 손님이 몰리기 전({range})에 진열을 한 번 봐주세요 —
  하루 매출의 {share_pct}%가 이때 나와요` 는 그 자체로 완결된 문장이고 필요한 값을 전부 담고 있다.
  그래서 2줄은 **전체 교체**로 구현한다. 1줄만 접두를 공유한다.

### ⚠️ 확인 요청

이 결정은 화면에 보이는 문장을 바꾼다. 명세 작성자가 변형 B에서 금액을 **의도적으로** 뺀 것이라면
(예: 단조로움 방지를 위해 아예 다른 각도의 문장을 노렸다면) 이 결정을 되돌려야 한다.
되돌리는 비용은 작다 — `briefing.py` 의 `LINE1_TEMPLATES` 에서 접두를 빼면 된다.

## 결정 2. 계산 JSON에 `dow_diff_pct_abs` 를 추가한다

### 문제

1줄 하락형 템플릿은 `{abs}` 를 치환한다 — `dow_diff_pct` 의 절댓값이다.
그런데 불변식 1은 이렇게 규정한다:

> 문장 계층(briefing 템플릿)은 계산 JSON 값의 치환만. **어떤 산술 연산도 금지**
> (반올림 포함 — 반올림은 JSON 저장 시점에 완료).

`abs()` 는 산술 연산이다. 문장 계층에서 계산하면 불변식 1을 어긴다.
그런데 명세 7.2의 JSON 스키마에는 절댓값 필드가 없다.

### 결정

계산 JSON에 `dow_diff_pct_abs` 를 추가한다. `aggregate`/`briefing` 계산 단계에서
`abs(dow_diff_pct)` 를 미리 구해 반올림까지 마친 값을 넣고, 템플릿은 그것을 치환만 한다.

같은 이유로 카드의 `lines` 에도 치환에 쓸 값을 **완성된 형태로** 담는다.
명세 7.2가 `"cards": [{"card_id": "G2", "lines": {...}}]` 로 `lines` 를 열어 둔 것이
바로 이 자리다.

- G2 카드 `lines`: `block_name`, `block_range`, `share_pct`
- G4 카드 `lines`: `subject_name`, `subject_pct`, `support_name`, `support_pct`
- G6 카드 `lines`: 비어 있음

특히 G4의 "건수·객단가 중 **절대값 큰 쪽을 주어로**"라는 판정(명세 7.4)은 비교 연산이므로
반드시 계산 계층에서 끝내고, 문장은 `subject_name`·`subject_pct` 를 치환만 한다.

### 근거

불변식 1은 "숫자는 코드만 만든다"는 이 프로젝트의 1번 원칙이고, 명세 2장이 충돌 시
가장 먼저 적용하라고 지정한 규칙이다. 명세 7.2의 필드 목록과 충돌하면 **불변식이 이긴다.**
필드를 늘리는 것은 명세를 어기는 것이 아니라 명세의 1번 원칙을 지키기 위한 필수 조치다.

또한 명세 10장의 `test_briefing_lines_use_only_json_numbers` — *"3줄 안의 모든 숫자가
JSON 값 집합에 존재"* — 는 절댓값이 JSON에 **있어야만** 통과한다. 명세가 요구한 테스트 자체가
이 필드의 존재를 전제한다.

## 결과

- 긍정: 문장 계층에 산술이 하나도 남지 않는다. `briefing.py` 의 렌더 함수는 `str.format` 만 부른다.
  이것을 테스트로 고정했다 — 렌더 함수 소스에 산술 연산자가 없음을 정적 검사한다.
- 긍정: 카드가 늘어나도 `lines` 규약만 지키면 문장 계층은 손대지 않는다.
- 부정: 계산 JSON이 명세 7.2 예시보다 필드가 많다. → 명세 7.2는 스키마 **예시**이고
  실제 계약은 "치환에 필요한 값이 전부 들어 있을 것"이다. JSON에 `schema_version` 을 넣어
  나중에 화면 쪽이 필드 유무를 판단할 수 있게 한다.
- 부정: 결정 1이 틀렸다면 문장이 바뀐다 (위 ⚠️ 참조).

## 명세와의 관계

- 결정 1은 명세 7.4의 **해석**이다. 명세의 접두 생략 표기와 폴백 규정을 근거로 삼았다.
- 결정 2는 명세 7.2 스키마의 **확장**이며, 불변식 1과 명세 10장 테스트가 요구하는 것이다.
- 두 결정 모두 명세 7.4의 **문자열 자체는 한 글자도 바꾸지 않았다.** 변형 목록도 그대로 2종이다.
