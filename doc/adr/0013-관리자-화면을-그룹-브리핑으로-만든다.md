# ADR-0013. 관리자 화면을 그룹 브리핑으로 만든다

- 상태: 채택
- 일자: 2026-08-28
- 관련 마일스톤: M7
- 결정자: 사용자 지시 ("여러 매장을 관리하는 관리자 화면", 이후 "보고서 형식", "실제는 1,300개 매장")

## 배경

명세 9장은 화면을 **점포장 1인용 1페이지**로 규정했다. 매장 셋을 맡은 사람의
질문은 다르다 — "오늘 당신 매장에서 무엇을 하라"가 아니라 **"오늘 어느 매장부터 볼 것인가."**

기존 구조로 그 답을 얻으려면 사이드바 selectbox를 세 번 바꾸고, 바꾸는 사이에
앞 매장 숫자를 기억해야 한다. 30초 안에 끝나지 않는다.

요구는 세 번에 걸쳐 커졌다.

1. "여러 매장을 관리하는 관리자 화면"
2. "자세히 보기보다 **보고서 형식**으로 — 집계와 매장별 매출 그래프"
3. "실제 환경은 **1,300개 매장**이니 고려해서"

## 결정 1. 명세 부록을 먼저 쓰고 코드를 쓴다

ADR-0012(결품 예상)에서 세운 순서를 그대로 따랐다.
`부록B_관리자화면.md` 에 화면 구성·문장·테스트를 확정한 뒤 구현했고,
요구가 커질 때마다 부록을 **개정**(B.10, B.13)한 다음 코드를 고쳤다.

**근거**: 명세 14장의 목적은 구현 중 즉흥적으로 기능이 붙는 것을 막는 데 있다.
소유자가 범위를 넓히는 것은 그 금지의 대상이 아니지만, 코드가 먼저 가면
"명세가 유일한 원천"이라는 원칙이 무너진다.

## 결정 2. 합계도 배치가 만든다 (부록 B.2)

가장 쉬운 구현은 화면이 매장 셋을 읽어 `sum()` 하는 것이다. 이것을 금지했다.

불변식 1은 "숫자는 코드만 만든다", 불변식 7은 "화면은 표시만"이다.
세 매장 매출을 화면이 더하면 **그 합계는 화면이 만든 숫자**가 된다.
합계 하나가 허용되면 다음은 평균, 그다음은 증감률이다.

그래서 `BRIEFING_DAILY_GROUP` 에 날짜당 1행을 저장하고 화면은 JSON 1건을 읽는다.
매장 화면이 3초에 뜨는 것과 같은 이유로 관리자 화면도 빠르다.

**정적 검사(`test_admin_view_makes_no_arithmetic`)가 이 경계를 지킨다.**
구현 중 실제로 두 번 걸렸다 — 캡션의 `len()` 과 문자열 `+` 연결. 둘 다 고쳤다.

## 결정 3. 기간 집계는 로더의 SQL이 한다 (부록 B.10)

보고서로 확장하면서 "최근 7일", "지난 기간 대비"가 필요해졌다.
결정 2를 그대로 적용하면 날짜마다 같은 숫자를 396번 저장하게 된다.

경계를 다시 그었다.

| 종류 | 만드는 곳 | 근거 |
|---|---|---|
| 기준일 요약 (합계·비중·상태·먼저 볼 매장) | 배치 | 상태와 먼저 볼 매장은 **카드 판정**에 의존한다. 매일 고정된 값 |
| 기간 집계 (최근 7·14일, 지난 기간 대비) | 로더의 SQL | 기간은 화면에서 고르는 축이라 저장 대상이 아니다 |

두 경우 모두 **화면은 산술을 하지 않는다.** `load_totals()` 가 이미 쓰던 방식이다.

## 결정 4. 총평을 문장으로 쓰지 않는다

"지난주보다 5.5% 늘었어요" 같은 문장을 화면이 만들면 화면이 문장 계층이 되어
불변식 7이 흔들린다. 값과 라벨로만 보여 준다 — `지난 7일 대비  +5.5%`.

## 결정 5. 신호를 JSON 밖 컬럼으로도 남긴다 (부록 B.13)

"최근 30일 중 재고가 며칠 부족했나"를 세려면 브리핑 JSON을 전부 열어야 한다.
매장 3개면 90건이지만 **1,300개면 화면을 열 때마다 39,000건**을 파싱한다.

`MART_DAY_STORE_SIGNAL(SALEDATE, DEPT_CD, STATUS, RISK_COUNT)` 를 더해
배치가 신호를 컬럼으로도 남긴다. 집계가 `GROUP BY` 한 번으로 끝난다.

**진실의 원천은 여전히 브리핑 JSON이다.** 이 테이블은 그것을 집계 가능한 모양으로
옮겨 적은 것이며, 두 값이 어긋나지 않음을 테스트가 고정한다
(`test_signal_table_matches_briefing_json`).

**같은 사실을 두 곳에 적는 것은 비용이다.** 그럼에도 택한 이유는, 대안이
"화면이 느려서 못 쓰는 것"이거나 "브리핑 테이블에 컬럼을 덧붙여 불변식 5를
건드리는 것"이었기 때문이다.

## 결정 6. 상한은 "적으면 전부"로 동작한다 (부록 B.13)

1,300개 대응이 데모(3개)를 망치면 안 된다. 모든 상한을 이렇게 뒀다.

| 상한 | 값 | 3개 매장일 때 |
|---|---|---|
| 그룹 요약 매장 행 | 20 | 3개 전부 |
| 그래프 계열 | 5 (+전체 합계) | 3개 전부 |
| 기간 합계 표 | 20 | 3개 전부 |
| 신호 반복 표 | 10 | 3개 전부 |

`stores_truncated` 가 `False` 면 화면은 잘렸다고 말하지 않는다.
**같은 코드가 3개에서도 1,300개에서도 돈다.**

## 결정 7. 자르기는 DB가 한다

1,300행을 파이썬으로 받아 `head()` 하지 않는다. `ORDER BY ... LIMIT` 으로
DB가 잘라서 준다. 상품 마트는 1,300개 환경에서 4,700만 행이 되므로 특히 그렇다.

기간 합계에서 이 원칙을 어긴 곳이 하나 있었고(전 매장 반환), 규모 시험에서 잡아 고쳤다.

## 결과

- 긍정: 관리자가 "오늘 어느 매장부터"를 한 화면에서 정한다. 매출 3위 매장이
  유일하게 재고가 부족해 맨 위로 지목되는 날이 있는데, 매출 표만 봐서는 나오지 않는 판단이다.
- 긍정: **팀장에게 건넬 파일**이 생겼다 (그룹 보고서 xlsx 4시트).
- 긍정: 1,300매장 × 40일을 실제로 만들어 검증했다 — 화면 1회 로더 합계 **313ms**,
  그룹 JSON **5,234 bytes**, 모든 표·그래프가 상한 안에 들어온다.
- 부정: 테이블이 2개 늘었다 (`BRIEFING_DAILY_GROUP`, `MART_DAY_STORE_SIGNAL`).
  발행 대상도 7개가 됐다.
- 부정: 신호가 두 곳(JSON·컬럼)에 있다. 어긋나면 관리자 화면이 거짓말을 한다 —
  테스트로 막았지만 구조적 비용이다.
- 부정: 명세 9장의 "1페이지" 약속이 화면 2종으로 늘었다. 점포장 화면은
  한 픽셀도 바꾸지 않았지만, 제품이 단순하다는 주장은 이전보다 약해졌다.
- 중립: `st.session_state` 제약(위젯 생성 뒤 키 변경 금지)에 걸려 배포가 한 번 죽었다.
  대기 키를 두고 다음 실행 맨 앞에서 옮기는 방식으로 고쳤다. 테스트가 버튼을
  **누르지 않아** 못 잡았던 것이라, 이후 상호작용은 눌러 보는 테스트를 쓴다.

## 명세와의 관계

- 명세 4장 DDL에 테이블 2개 추가 (기존 11개 불변).
- 명세 7장에 그룹 브리핑·신호 마트 생성 단계 추가 (기존 카드·문장·임계값 전부 불변).
- 명세 9장에 보기 전환과 화면 1종 추가 (기존 점포장 화면 불변).
- 명세 14장의 금지(전문용어·원인 단정·발주 수량)를 새 화면·보고서에 그대로 적용.
- 불변식 1·3·7 유지. 화면 무산술은 정적 검사로 고정.
