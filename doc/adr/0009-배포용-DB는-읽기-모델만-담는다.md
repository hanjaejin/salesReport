# ADR-0009. 배포용 DB는 읽기 모델만 담고, 폐기 예정 Streamlit API를 쓰지 않는다

- 상태: 채택
- 일자: 2026-08-27
- 관련 마일스톤: M5

배포를 실제로 해 보니 명세대로는 성립하지 않는 것이 둘 있었다. 둘 다 명세가 쓰인 뒤
바뀐 외부 조건(파일 크기, 라이브러리 API) 때문이며, 명세의 **의도**를 지키는 쪽으로 정했다.

---

## 결정 1. 배포용 DB에서 FACT 3종을 비운다

### 문제

명세 15장은 이렇게 적었다.

> 저장소 — GitHub 공개/비공개 저장소 — 코드 + **구축 완료 SQLite DB 동봉**
> (`data/pos_mockup.db`, **수십 MB 이내**). 데모는 읽기 중심이라 클라우드에서
> 파이프라인 재실행 불필요

13개월 전체를 구축한 실제 크기는 **171MB** 였다 (VACUUM 후).

| 항목 | 값 |
|---|---|
| FACT_RECEIPT | 463,544행 |
| FACT_RECEIPT_ITEM | 685,917행 |
| FACT_PAYMENT | 486,840행 |
| MART 3종 + BRIEFING_DAILY | 132,786행 |
| **전체 파일** | **171.1 MB** |

명세의 "수십 MB 이내"를 크게 넘고, 더 결정적으로 **GitHub의 파일당 100MB 한도를 초과**한다.
그대로는 저장소에 올릴 수 없고, 따라서 Streamlit Community Cloud 배포 자체가 불가능하다.

### 결정

배포용 DB에서 **FACT 3종을 비우고 VACUUM** 한다. 파이프라인 CLI에 `--deploy` 플래그를 두어
구축 직후 같은 명령으로 처리한다.

```bash
python -m src.load.pipeline --from 20250701 --to 20260731 --deploy
```

| | 크기 |
|---|---|
| 전체 (FACT 포함) | 171.1 MB |
| **읽기 모델만** | **17.9 MB** (10.5%) |

### 근거

- **화면은 FACT를 읽지 않는다.** `app/main.py` 가 조회하는 테이블은 `BRIEFING_DAILY`,
  `MART_*` 3종, `DIM_STORE`, `FEEDBACK_LOG` 뿐이다. FACT는 `aggregate` 가 마트를 만들 때만 읽는다.
  즉 배포되는 것은 **읽기 모델**이고, 원장은 그것을 만드는 재료다.
  명세가 "데모는 읽기 중심"이라고 한 바로 그 성질이다.
- **관리자 [최근 7일 재생성] 버튼이 그대로 동작한다.** `load_period()` 는 FACT를
  DELETE 후 Extractor에서 새로 만들어 넣는다. 비어 있어도 DELETE가 무의미할 뿐 결과는 같다.
  오히려 **더 강한 시연**이 된다 — 원장 없이 시작해도 같은 숫자가 나온다.
- **FACT는 언제든 되살릴 수 있다.** 파생 시드가 결정적이므로(ADR-0005) 같은 명령을
  `--deploy` 없이 돌리면 한 글자도 다르지 않은 원장이 142초 만에 복원된다.
  **재현 가능한 것을 저장소에 넣지 않는다**는 것은 일반적인 규율이기도 하다.

### 결과

- 긍정: 17.9MB로 GitHub·Streamlit Cloud 양쪽 제약을 만족한다.
- 긍정: 저장소 클론이 가볍다.
- 부정: 배포본에서는 원장 수준의 재조회가 안 된다 (예: 특정 영수증 추적).
  데모 화면에 그런 기능이 없으므로 영향 없다.
- 부정: `--deploy` 를 쓴 DB로 마트를 다시 만들면(FACT가 비었으므로) 마트가 비게 된다.
  → `--deploy` 는 **구축을 마친 뒤 마지막에** 쓰는 플래그임을 CLI 도움말과 README에 명시하고,
  이미 비어 있는 기간에 대해 경고를 남긴다.

## 결정 2. `use_container_width` 대신 `width="stretch"` 를 쓴다

### 문제

명세 9장은 화면 스타일을 이렇게 지정했다: *"버튼 `use_container_width=True`"*.

현재 Streamlit(1.51.0)은 실행 시마다 경고를 낸다.

```text
Please replace `use_container_width` with `width`.
`use_container_width` will be removed after 2025-12-31.
```

`requirements.txt` 가 `streamlit>=1.40` 이므로 Streamlit Community Cloud는 최신 버전을 설치한다.
파라미터가 제거된 버전이 깔리면 **발표 당일 화면이 뜨지 않는다.**

### 결정

`width="stretch"` 로 바꾸고, `requirements.txt` 의 하한을 `streamlit>=1.49` 로 올린다
(`width` 파라미터가 들어온 버전). 정적 검사 테스트가 폐기 API의 재유입을 막는다.

### 근거

명세 9장이 요구한 것은 **"버튼을 가로로 꽉 채운다"는 동작**이고,
`use_container_width` 는 명세를 쓰던 시점의 API 이름이었다. 같은 동작을 현재 API로 낸다.
이름을 그대로 지키면 동작이 사라진다 — 지켜야 할 것은 동작이다.

### 결과

- 긍정: 배포 환경의 Streamlit 버전이 올라가도 깨지지 않는다.
- 긍정: 실행 로그에서 경고가 사라져 발표 중 터미널이 깨끗하다.
- 부정: 명세 9장 문구와 코드가 글자 단위로 다르다. → 이 ADR과 테스트 docstring에 근거를 남긴다.
- 부정: Streamlit 1.40~1.48 에서는 동작하지 않는다. → `requirements.txt` 하한을 올려 막는다.

## 명세와의 관계

- 결정 1은 명세 15장의 **"수십 MB 이내"라는 제약을 지키기 위한** 조치다.
  명세가 예상하지 못한 데이터 규모에 대응한 것이지 요구를 축소한 것이 아니다.
- 결정 2는 명세 9장의 **동작 요구를 지키기 위해** API 이름을 바꾼 것이다.
