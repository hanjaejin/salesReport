# 부록 B. 여러 매장 관리자 화면

> 본 명세 `30초매장브리핑_바이브코딩_구현설계서_v1.3.1.md` 의 확장이다.
> 본문과 충돌하면 **본문이 이긴다.** 이 부록은 본문 9장(화면)이 규정한
> "점포장 1인용 1페이지"에 **보는 사람 한 종류를 더한다.**
>
> 관련: [ADR-0013](adr/0013-관리자-화면을-그룹-브리핑으로-만든다.md)

## B.1 왜 넣는가

지금 화면은 점포장에게 "오늘 당신 매장에서 무엇을 하라"를 말한다.
매장 셋을 맡은 사람에게는 그 질문이 다르다 — **"오늘 어느 매장부터 볼 것인가."**

현재 구조로 그 답을 얻으려면 사이드바 selectbox를 세 번 바꿔야 하고,
바꾸는 사이에 앞 매장 숫자를 기억해야 한다. 30초 안에 끝나지 않는다.

세 매장의 판단 재료는 **이미 다 만들어져 있다.** `BRIEFING_DAILY` 에
매장별로 매출·손님·1인당·카드·위험재고가 들어 있다. 새로 계산할 것이 아니라
**한 화면에 모으는 문제**다.

## B.2 절대 조건 — 화면은 여전히 계산하지 않는다

가장 쉬운 구현은 화면이 매장 셋을 읽어 `sum()` 하는 것이다. **이것을 금지한다.**

불변식 1은 "숫자는 코드만 만든다", 불변식 7은 "서버측 생성 — 화면은 표시만"이다.
세 매장 매출을 화면이 더하면 **그 합계는 화면이 만든 숫자**가 된다.
합계가 하나 허용되면 다음은 평균, 그다음은 증감률이다. 경계는 처음에 긋는다.

그래서 그룹 요약도 **배치가 만들어 저장하고, 화면은 JSON 1건을 읽어 표시만 한다.**
매장 화면이 3초 안에 뜨는 이유와 같은 이유로, 관리자 화면도 빠르다.

## B.3 스키마 — `BRIEFING_DAILY_GROUP` 추가

본문 4장 DDL에 테이블 **1개**를 더한다. 기존 테이블은 한 글자도 바꾸지 않는다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `SALEDATE` | TEXT | `YYYYMMDD` (PK) |
| `PAYLOAD_JSON` | TEXT | 그룹 요약 JSON (B.5) |

점포 단위가 아니므로 `DEPT_CD` 가 없다. 날짜 하나에 행 하나다.

**`BRIEFING_DAILY` 에 `DEPT_CD='ALL'` 로 끼워 넣지 않는다** — `DIM_STORE` 에 없는
점포코드를 만드는 셈이라 참조 관계가 무너지고, 매장 목록 질의마다 예외가 생긴다.

## B.4 생성 규칙 (본문 7장 확장)

**매장별 브리핑이 전부 만들어진 뒤에** 그 날짜의 브리핑들을 읽어 만든다.
원장이나 마트를 다시 집계하지 않는다 — 이미 확정된 값을 모으기만 한다.

```
build_briefings(...)          # 기존: 매장별 브리핑 저장
  └─ build_group_briefing(...)  # 추가: 그 날짜 브리핑들을 모아 1건 저장
```

멱등은 기존과 같다 — 날짜 단위 DELETE→INSERT (불변식 3).

### 정렬

매장 행은 **매출 내림차순 고정**이다. 매일 순서가 바뀌면 관리자가
"둘째 줄이 어느 매장이었지"를 매번 다시 읽어야 한다.

대신 **먼저 볼 매장**을 따로 하나 뽑아 위에 적는다. 우선순위는 본문 7.3의
카드 우선순위를 그대로 쓴다.

| 순위 | 조건 | 뜻 |
|---|---|---|
| 1 | `G3` 발동 (재고 부족) | 오늘 채워야 한다 |
| 2 | `G2` 발동 (시간대 쏠림) | 진열 시점이 있다 |
| 3 | 없음 | 조용한 날 |

같은 순위가 여럿이면 **매출이 큰 매장**이 앞선다. 아무 매장도 1·2위가 아니면
"먼저 볼 매장"은 비운다 — 침묵할 줄 아는 것이 이 제품의 신뢰 조건이다 (본문 7.3).

## B.5 계산 JSON

```json
{
  "schema_version": 1,
  "saledate": "20260609",
  "store_count": 3,
  "total_sale_amt": 4409450,
  "total_deal_cnt": 1353,
  "group_avg_ticket": 3259,
  "attention_dept_cd": "901001",
  "attention_count": 1,
  "stores": [
    {
      "dept_cd": "901001",
      "dept_nm": "중앙역 대형점",
      "sale_amt": 2999800,
      "deal_cnt": 929,
      "avg_ticket": 3229,
      "dow_diff_pct": 33.4,
      "dow_baseline_available": true,
      "status": "STOCK",
      "status_text": "재고 7개 부족",
      "risk_count": 7
    }
  ]
}
```

- `group_avg_ticket` 은 **총매출 ÷ 총손님** 을 마트 계층에서 반올림해 넣는다.
  매장별 1인당 구매액의 평균이 아니다 (손님 수가 다르므로 값이 달라진다).
- `total_deal_cnt` 가 0이면 `group_avg_ticket` 은 0이다 (0 나눗셈 금지 — 본문 7.2와 동일).
- `status` 는 `STOCK` · `PEAK` · `CALM` 셋뿐이다. 매장 브리핑의 2줄을 차지한 카드와 **항상 일치**한다.
- `attention_dept_cd` 는 없으면 `null`.

## B.6 문장 (본문 7.4 확장)

관리자 화면에 새 **브리핑 문장**은 만들지 않는다. 매장 문장은 그 매장 것이고,
여기서는 **상태 라벨**만 쓴다. 라벨 목록이 전부이며 임의 변형을 금지한다.

| status | 라벨 | 색 |
|---|---|---|
| `STOCK` | `재고 {risk_count}개 부족` | 🔴 |
| `PEAK` | `{peak_name}에 몰림` | 🟡 |
| `CALM` | `조용한 날` | ⚪ |

먼저 볼 매장 한 줄:

```
오늘은 {dept_nm}부터 확인해 보세요
```

아무 매장도 해당 없으면:

```
오늘은 세 매장 모두 평소대로예요
```

### 지켜야 할 금지 (본문 14장 그대로)

- 발주 수량·재고 수치 상세 금지 (부록 A.5와 동일).
- 전문용어 금지 — `분석`·`예측`·`객단가`·`증감률`·`결품`·`리드타임` 을 쓰지 않는다.
- 매장 간 우열을 단정하는 문장 금지. "A매장이 부진합니다" 같은 평가는 만들지 않는다.
  숫자를 나란히 보여 주고 판단은 사람이 한다.
- 원인 단정 금지 — "비 때문에" 같은 문장은 데이터에 근거가 없다.

## B.7 화면 (본문 9장 확장)

사이드바 맨 위에 **보기 전환** 하나를 둔다.

```
◉ 점포장 화면      ← 기본값 (기존 화면 그대로)
○ 여러 매장 보기
```

멀티페이지(`pages/`)를 쓰지 않는다 — 발표 중 페이지 이동은 흐름이 끊기고,
URL이 바뀌어 되돌아오기 어렵다.

**여러 매장 보기** 구성 (위에서부터):

1. 헤더 — `{날짜} · {store_count}개 매장` + 목업 배지 (상시)
2. 먼저 볼 매장 한 줄 (B.6)
3. 매장 표 — 매장명 · 어제 매출 · 손님 · 1인당 · 상태 라벨
4. 합계 줄 — 총매출 · 총손님 · 1인당
5. 하단 고지 (본문 9장과 동일)

매장 행을 누르면 그 매장의 점포장 화면으로 넘어간다 — 관리자가
"어느 매장부터"를 정한 다음 바로 그 매장을 볼 수 있어야 한다.

기존 점포장 화면은 **한 픽셀도 바꾸지 않는다.**

## B.8 테스트 (본문 10장 확장)

| 테스트 | 확인 |
|---|---|
| `test_group_totals_match_store_sum` | 그룹 합계 = 매장별 값의 합 (DB에서 각각 읽어 비교) |
| `test_group_avg_ticket_is_total_based` | 1인당 = 총매출÷총손님 (매장 평균이 아님) |
| `test_group_avg_ticket_zero_deals` | 손님 0명이면 0 (0 나눗셈 없음) |
| `test_group_status_matches_store_cards` | `status` 가 매장 브리핑의 2줄 카드와 일치 |
| `test_group_store_order_is_by_sale_amt` | 매출 내림차순 고정 |
| `test_attention_follows_card_priority` | G3 > G2 > 없음, 동순위는 매출 큰 쪽 |
| `test_attention_is_null_when_all_calm` | 모두 조용하면 먼저 볼 매장 없음 |
| `test_group_briefing_is_idempotent` | 같은 날짜 재실행 시 동일 |
| `test_admin_view_makes_no_arithmetic` | 관리자 화면 함수에 산술 연산 없음 (AST 정적 검사) |
| `test_admin_view_shows_no_jargon` | 금지 용어 0개 |
| `test_admin_view_renders_without_exception` | AppTest 로 실제 렌더링 |

`test_admin_view_makes_no_arithmetic` 이 이 부록의 **핵심 방어선**이다.
화면에 `sum()` 이나 `+` 가 들어오는 순간 깨진다.

## B.9 배포

`BRIEFING_DAILY_GROUP` 은 화면이 읽으므로 **읽기 모델**이다 —
`publish.READ_MODEL_TABLES` 에 넣는다 (ADR-0011). 396행이라 발행 시간에 영향이 없다.

## 명세와의 관계

- 본문 4장 DDL에 테이블 1개 추가 (기존 11개 불변).
- 본문 7장에 그룹 브리핑 생성 단계 추가 (기존 카드·문장·임계값 전부 불변).
- 본문 9장에 보기 전환과 화면 1종 추가 (기존 점포장 화면 불변).
- 본문 14장의 금지(전문용어·원인 단정·발주 수량)를 새 화면에도 그대로 적용한다.
- 불변식 1·3·7을 그대로 지킨다. 특히 **화면 무산술**은 테스트로 고정한다.
